# MEDS v8.1 — Leader H250 capacity pass

Status: implementation and synthetic capacity verification; production stays paused.
Engine: `meds-v8.1-leader250-capacity`. Strategy/accounting entry version: `leader-hunt-v8.1-leader250-capacity`. Schema: 11.

## Scope and account

`LEADER_ONLY=true` routes scheduled and manual scans directly to Leader research and the H250 book. `SCOUT_ENABLED=false`, `PAPER_ENABLED=false`, `crons=[]`, and shadow-only execution remain configured. No reporting schedule or brokerage execution was added.

Migration 0005 upgrades the existing v8 database. H250 is inserted once with $250 cash and starting capital. Reapplying it cannot reset cash or performance. `leader_runtime_config` designates H250 as the sole active account. H100/H1K/H10K/H100K/H500K are inferred inactive without updating their account, position, trade, event, drawdown or telemetry rows. Normal MEDS implementation and historical tables remain available.

The account retains the v8 12% capital reserve ($30), 4% starting-capital target per entry ($10), fractional paper equities, whole option contracts, observed-side adverse slippage, 5% minute participation, combined 32-position limit, duplicate-underlying checks and cooldown. Options that cannot fit the $10 target are rejected with `OPTION_CONTRACT_TOO_EXPENSIVE`; no trade is a valid result. No strategy thresholds or profit-taking fractions are increased to manufacture activity.

## Runtime changes

Removed from the active path: normal paper-lab scans/decisions/entries/exits/valuations; legacy shadow/Leader position managers; all historical capital-tier loops; legacy signal/observation writes and alert delivery; per-symbol discovery/decision/outcome writes; per-position quote-health writes; per-write lease renewals; runtime schema migrations.

The new path loads one account, its open inventory, lifecycle state, pending exit intents, cooldowns, relevant symbol state, retained held marks and current-day research shards. Decisions and accounting are calculated in memory. JSON `INSERT ... SELECT FROM json_each(?)` and `UPDATE ... FROM json_each(?)` submit one statement per changed table set. Each SQL statement is counted independently inside `batch()`.

All fills, cash changes, lifecycle events, valuation, research evidence and cycle completion commit in one fenced transaction. Revision checks prevent a stale book from committing. An audit failure rolls back fills. A pause or replaced lease rejects the transaction. If only the subsequent metric enrichment fails, the already committed accounting remains a reported success with a warning.

Existing event-time indexes are replaced with account/position/event indexes, and duplicate-event triggers constrain their lookups by account. This preserves the same uniqueness rule for globally unique position IDs, avoids scanning historical accounts, and keeps one secondary index per event table. No historical event row is changed. CI includes 5,000 old-account events.

## Audit evidence and reporting

`leader_cycle_audit` stores the complete final research universe, shortlist, account decisions and exact rejections, full source gainer board, and calculated top-mover audit in one durable JSON record. This eliminates duplicate copies in per-symbol observation, board and mover tables. Legacy rows in those tables are retained.

Sixteen small research shards per session retain first provider appearance, first seen/source/price/change, first shortlist/runner/executable times, first and early rejection, entry and sampled high/low. Changed shards are ingested in one statement. Payloads above the D1-safe bound fail the cycle rather than silently dropping evidence.

Read-only endpoints:

- `/status`: H250 active; old tiers under `historical_accounts`; normal MEDS `HISTORICAL_INACTIVE`.
- `/status/hunt/positions`: active H250 positions; `?historical=true` includes historical positions.
- `/status/hunt/research?symbol=SYMBOL`: detailed cycle evidence and session outcomes with sampled MFE/MAE.
- `/status/hunt/decisions?symbol=SYMBOL`: new account decisions; `?version=legacy` preserves legacy access.
- Existing gainer-audit endpoint: reads the new cycle record; `?version=legacy` reads retained v8 evidence.
- `/status/hunt/performance`: defaults to the new entry version. Explicit old versions and `version=all` remain available.

Historical normal endpoints remain queryable. Current performance does not include old-tier gains/losses. MFE/MAE means sampled research excursion, not continuous-market or executable-fill hindsight.

## Capacity gate and its limits

`v8.1-capacity-measurements.json` records real local workerd/D1 metadata from CI. Fixture initialization and post-run verification queries are excluded; every runtime SQL statement, control query, atomic-batch member and final metric update is included. SQLite-only test placeholders explicitly report unavailable row metrics.

The mixed maximum fixture includes 260 discovered symbols plus 32 mandatory held underlyings (292 scanned), both equity and option management, nine new entries, 17 closures, ladder sales, a partial-exit intent, reserve/shared-capacity checks, top-mover audit, full rejection evidence, valuation and a milestone write. Its prior realized gains exercise the milestone path without altering the $250 starting-capital policy. Separate fixtures cover 32 simultaneous equity ladders, entry-only, unaffordable options, provider failure and successful held-quote recovery.

| Fixture | Provider requests | SQL statements | Rows read | Rows written |
|---|---:|---:|---:|---:|
| Mixed entries/exits, partial intent, milestone | 16 | 34 | 1270 | 500 |
| 32 equity ladders and +200 trims | 12 | 25 | 1639 | 536 |
| Six equity entries | 19 | 24 | 109 | 150 |
| Held-provider outage and retries | 8 | 20 | 168 | 43 |
| Eight unaffordable option chains | 19 | 21 | 65 | 117 |

Every fixture uses 13 D1 API calls; the SQL column counts statements inside those calls. The largest measured query count leaves 16 queries (32%) below the 50-query ceiling. The largest measured row count projected across 151 cycles is 247,489 reads and 80,936 writes, leaving approximately 19% of the 100,000-write daily allowance before other database use.

The configured runtime budget is 40 submitted SQL statements, below the Free ceiling of 50. Fixture measurements do not establish production CPU time. Workers Free allows only 10 ms CPU; Node test duration and local D1 SQL duration are not that measurement.

Daily projections use 151 planned session-cadence cycles (78 regular, 33 premarket, 24 postmarket, 16 overnight). They are conservative arithmetic projections, not a measured live day. Reporting and other database users also consume the shared daily quotas. Historical-volume indexing is tested, but unbounded account history must still be monitored.

The cycle audit is approximately 0.27–0.30 MB in these fixtures: roughly 41–45 MB per 151-cycle day before other table/index growth. The Free per-database size ceiling is 500 MB. Preserving history therefore requires a measured remaining-storage budget and an archival plan before a sustained restart. No history was deleted to make a capacity number pass.

**Verdict: the per-invocation D1 query bottleneck is resolved in the measured fixtures. Full Workers Free production readiness is not yet proven because CPU and retained-storage runway remain unverified. Keep MEDS paused.** A later manual restart must establish those remaining gates; this change does not authorize or perform one.

## Validation

CI runs functional/regression tests, real local D1 capacity fixtures, TypeScript checking and a Wrangler deployment dry run. The position-management parity test compares the v8 and v8.1 books for identical cash, quantities, realized accounting and lifecycle state. Additional tests cover historical immutability, capital reconciliation, idempotent migration, duplicate-cycle prevention, missing marks, successful retry, audit rollback, pause races and postcommit metric failure.

Production verification must confirm the new version/schema and H250 account while disabled, compare historical balances/positions/trade counts with the predeployment snapshot, and confirm native Cloudflare deployment success. No market cycle should be run in production during verification.
